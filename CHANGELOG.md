# Changelog

All notable changes to SAFE-Starter-Kit are documented here.

Every release entry states the **SAFE compatibility baseline**: the SAFE version and commit the release was checked against. A newer SAFE version never makes a release compatible with that version automatically. Compatibility is only claimed for the baseline written in the entry, and it does not mean certification or legal compliance.

## Unreleased

Changes after 0.2.0 go here.

### Added
- Case links have a type (duplicate, related or root and sub-case), a required reason and a visibility checkbox that is off by default (migration 0052; links made before it read as related with no reason). A duplicate link closes the duplicate case in the same step and is refused while that case has an open deadline task. A root and sub-case link lets a reader of the sub-case read the root case, read only. With the checkbox on, the users of either case can see both cases. The API, the CLI and the case page take the new fields.
- Deadlines: the 30-day analysis obligation is a deadline task of its own, `preliminary_control_failure_analysis`. It is due 30 elapsed days after t0, at the same time as the preliminary public report task, so a weekend or a holiday does not move it. Each new case gets it with its other tasks, and it moves with t0 like them. It is not an external notice, so the internal incident option does not change it. Migration 0051 adds it to the cases that already exist, once per case.

### Changed
- The default stack (`compose.yaml`) runs in production mode: `SAFE_MODE=production` for `api` and `worker`, with no demo dataset, so the sign-in page takes a username and password. The demo is an overlay: `scripts/demo.sh` starts it with `compose.demo.yaml`, which sets demo mode and the synthetic dataset for `api` and `worker`.

## 0.2.0 - 2026-11-03

**SAFE compatibility baseline:** SAFE v1.0 (2026-10-21), wg-safe commit `08c0d6a11163d10ac878a15dc9f53b5b322fd7cb`. This version is not tagged in git yet.

### Added
- Single-organization self-hosted stack (Docker Compose): PostgreSQL, one-shot migrations, API, worker, nginx gateway, container CLI.
- Username and password login with Bearer JWT, refresh-token rotation, logout, rate limiting, forced password change.
- Password policy: passwords expire after 180 days, and a new password may not reuse the last three passwords or any temporary password issued to the account.
- First admin created once from the command line; first admin is protected and cannot be disabled, deleted, or demoted.
- Admin user management: list, role and status changes, soft delete, password reset. Editable role-permission matrix.
- Soft delete for every table, with `created_at`, `updated_at`, `deleted_at`, `is_deleted`.
- Audit log (append-only) and transactional outbox with a worker.
- Minimal case domain: create a case from an awareness time (t0) and calculate SAFE notification deadlines.
- Personal data inventory (metadata only) with JSON and CSV export.
- System timezone chosen at first admin login; changes are confirmed and audited.
- React and TypeScript web UI, container CLI with case commands.
- HTTPS-only gateway with a development certificate authority (`scripts/make-dev-cert.sh`) and HSTS.
- Case lifecycle: assignment, deadline status per task, closing and reopening with stored reasons, and case history. Reasons and evidence events are shown only to roles that hold the matching permission.
- Revisions for child records (migration 0050): a deadline task, a legal duty and a user account each have a revision, which starts at 1 and rises only when a field really changes. `PATCH /api/v1/cases/{case_id}/deadlines/{task_id}`, `PATCH /api/v1/cases/{case_id}/legal-duties/{duty_id}` and `PATCH /api/v1/users/{user_id}` need `If-Match` with the revision that was read, and answer `428`, `400` (`invalid_if_match`) and `412` (`precondition_failed`, with `current_revision`) like the other revision checks. The deadline task ETag is the task revision, the legal duty ETag is the duty revision, and the user ETag is the account revision. A change to one of these records does not raise the case revision. This is deliberate, so a deadline task ETag and a case ETag are different numbers. The revision of a deadline task also rises when the recalculation of SAFE due dates or the weekly update task changes it, and when a deadline is restored; the restore route does not check `If-Match`.
- `safe-kit case task update` and `safe-kit case legal-duty update` take `--revision` as optional. Without it, the command reads the current revision of the task or duty and sends that. Give `--revision` to check the change against a revision you read earlier.
- Case review as review rounds: a round opens eleven template layers, each unset until an assigned reviewer records an outcome with a reason. Review notes are shown only to callers with `cases:read_all`; other callers see the outcome and time. The single-outcome case reviews of earlier builds are kept as one layer, `legacy-case-review`.
- Evidence: upload, download, and a custody record for each event. Files are encrypted with AES-256-GCM, keys come from a file, and uploads have a size limit and a media-type allowlist. New permission `evidence:read`; `evidence:write` is needed to upload.
- Evidence verification: an upload becomes available only after the stored object is read back and checked with the download rules. The worker marks uploads that stay pending for 30 minutes as failed.
- Case import from a versioned JSON file (`import_format_version` 1), through the API and `safe-kit case import`. Each record reports imported, duplicate, conflict, rejected, or failed.
- Synthetic demo dataset (`python -m safe_kit.demo_seed seed`), refused unless `SAFE_MODE=demo` and `SAFE_DATASET=synthetic-demo`. It is idempotent. Each demo role (administrator, reporter, triager, investigator, reviewer, disclosure approver, auditor) has its own random credential, stored only as a hash. The plain value is written once to a file per role in the directory named by `SAFE_DEMO_CREDENTIAL_DIR` (mode 0600). The demo administrator's file is still the one named by `SAFE_DEMO_CREDENTIAL_FILE` when that is set. Demo sign-in works only on loopback, in demo mode, with a demo username and its credential. The login screen lists the demo roles in demo mode. The seeded cases are assigned to the investigator and the reviewer, so those roles see them; the triager and the approver read every case by their real permissions.
- Existing demo databases (seeded before per-role credentials) get the new credentials once, with the directory set: `SAFE_DEMO_CREDENTIAL_DIR=/path/to/dir python -m safe_kit.demo_seed upgrade`. The administrator's credential does not change.
- Demo sign-in for the container CLI: `--demo-username` and `--demo-credential-file` (or `SAFE_DEMO_USERNAME` and `SAFE_DEMO_CREDENTIAL_FILE`) sign in through `POST /api/v1/demo/sign-in` instead of the password login. Only the first line of the file is read and the value is never printed. `scripts/demo.sh cli-show` runs the CLI on the host through the loopback gateway, because the API accepts demo sign-in only from loopback or `SAFE_DEMO_HOST_ADDRESS`, not from the CLI container.
- Loopback demo start script `scripts/demo.sh` (`start [--timeout N]`, `status`, `cli-show CASE_ID`) with its own compose project and overlay; the demo application and worker are on an internal network with no route out, the API is no longer published, and `scripts/demo-egress-check.sh` checks the DNS, IPv4 and IPv6 denial from inside the API container.
- Demo readiness: `scripts/demo.sh status` and `start` report ready only when this project's own gateway container is running and the API behind it answers. Another Compose project may hold the same loopback port. The demo banner is shown only when the server reports demo mode with the synthetic dataset.
- Optional `SAFE_TRUSTED_PROXIES` (IP addresses or CIDR ranges). The API reads `X-Forwarded-For` only from these proxy addresses, and the gateway overwrites that header with the address of its peer. The login rate limits and demo sign-in use the resolved client address.
- Profile fields (first name, last name, title, email); the top bar shows the full name and username.
- Test suites for the backend and the frontend, with coverage measured by the commands in the README.
- Case record: awareness events (incident, near miss, or blocked attempt, with the awareness kind and basis), impacts for each of the six plan areas (an area without a row is reported as not assessed), legal duties with their own due dates that never change deadlines, and a classification stored as versions with the five R01 trigger values. Each classification update must give the expected version. Migrations 0023 and 0024. Writes need `cases:triage`.
- Preliminary report for a case, which lists the missing fields instead of refusing. It needs `cases:read_all`.
- Free text in case records is returned only to callers with `cases:read_all`, as close reasons and review notes are. Audit rows keep only the length of the text.
- Reporter channel: `POST /api/v1/reports` opens a case for a signed-in reporter account and stores an optional follow-up contact (up to 200 characters) apart from the case content (migration 0021). The reporter account is never returned, and the case history hides the actor of the case-creation entry for every caller.
- Reporter contact: readable only with the new permission `reporter_contact:read`, which no role holds by default (migration 0022). Every read is audited. A triager (`cases:assign`) sees a reporter-channel case before it has an assignee, so it can assign an investigator or reviewer; the reporter identity and the contact stay hidden from it, and the contact still needs `reporter_contact:read`. Other `cases:read_all` callers, such as the disclosure approver, see such a case only once it has an active assignment. An administrator cannot reset the password of a reporter account.
- Case search: `GET /api/v1/cases` takes `q`, which matches the reference (partial, case-insensitive) or the start of the case ID. The header search uses it. Search only narrows the cases the caller can already see.
- Case list: `GET /api/v1/cases` takes `status` (`open` or `closed`), each case shows its next open deadline and its last update time, and the case list screen and `safe-kit case list` show both.
- Case visibility is checked in one place for case reads, lists, history, assignments, reviews, and evidence. An import response names an existing case only when the caller can see it.
- Sessions end after 60 minutes without activity and at most 12 hours after login. The browser renews the token pair on the first request made more than five minutes after the last renewal; refresh tokens rotate on every renewal.
- Browser sessions use HttpOnly cookies: `safe_access`, and `safe_refresh` (sent only to `/api/v1/auth`). The page reads the `safe_csrf` cookie and sends its value as the `X-CSRF-Token` header on state-changing requests. The CLI and API clients use `Authorization: Bearer`. Token and session lifetimes are required settings with no built-in defaults.
- Saving a case classification requires `cases:read_all` as well as `cases:triage`. Without it the save is refused, because it would clear the free-text fields the caller cannot see.
- Rate limits at the gateway: login is limited to 10 requests per minute per client, with a burst of 5, and the API to 30 requests per second, with a burst of 60. Excess requests get `429`. The API also keeps login counters in PostgreSQL, per username and per client, over a 15-minute window.
- Validation errors no longer repeat the rejected input, so a submitted password is not echoed back.
- Case record screens on the case detail page: awareness events, impacts, legal duties, classification with version checks, and the preliminary report.
- Reporter contact: the contact is read on request only, and each read is audited. The button sits under the note that reading is recorded in the audit log.
- Case assignments: a picker lists the users who may be assigned, from the new `GET /api/v1/cases/{case_id}/assignable-users`, which requires `cases:assign`.
- CLI case updates: `case close`, `case reopen`, `case assign`, `case unassign`, `case review record`, `case classification set`, `case impact set`, `case legal-duty add` and `update`, `case awareness add`. Each command logs in with a password prompt (or stdin), keeps the tokens in memory for that command, and ends the session afterwards. Nothing is written to disk.
- The inactivity watch signs out after 60 minutes without an API request and warns five minutes before. Mouse and keyboard use do not count as activity.
- The admin role cannot hold case or reporter contact permissions. `PUT /api/v1/rbac/roles/admin/permissions` answers `409` for such a set.
- No role can be granted `reporter_contact:read` through the role matrix. The matrix answers `409` with `reporter_contact_not_grantable`.
- Reporter contact can be read while the case is open, or within 72 hours after it was closed. Later reads are refused with `409` `reporter_contact_window_closed`, and the refused read is not audited.
- Assignees are chosen by the `cases:assignable` permission, granted to investigator and reviewer by migration 0026. `GET /api/v1/cases/{case_id}/assignable-users` lists them for users with `cases:assign`.
- Classification version conflicts answer `409` with `classification_version_conflict` and the current version, so clients do not parse text.
- SAFE deadlines start from the earlier of the case awareness time and any operator awareness event. A later operator event never delays them.
- A `reporting_owner` role holds `reporter_contact:read` and `cases:read_all` (migration 0029). It is the only role that can hold the contact grant. Its permission set is fixed: the role matrix answers `409` `reporting_owner_fixed` for any change to it. Admin can assign the role, and each assignment is audited. The role reads the content of every case, not only the contact, because the contact route needs `cases:read_all` to reach a case without an assignee.
- CLI read commands for case records: `case classification show`, `case impact list`, `case legal-duty list`, `case awareness list`, and `case report show` (needs `cases:read_all`).
- Classification has an explicit `none_applies` trigger (migration 0027). It cannot be combined with other triggers.
- The internal incident option works per task. Each external notice task is marked not applicable on its own, with a reason, through the deadline update. The case-wide switch is gone: a classification that sends `internal_incident_option` is refused with `400`. Migration 0037 gives each case that had the switch the same per-task exceptions, with the reason recorded as migrated. `POST /api/v1/cases/{case_id}/deadlines/{task_id}/restore` turns one exception off and returns the task to its previous status. Due dates do not change.
- An appeal on a review round names no reviewer. The system names the independent reviewer: the eligible reviewer with the fewest open appeals, then the lowest user ID. A request that names a reviewer is refused with `422`. When no reviewer is eligible, the appeal is refused with `409` `no_eligible_reviewer` and nothing is stored.
- Linked cases: two cases can be linked as a record only (migration 0028). Links change no task, deadline or status. Links are added, listed and removed from the case detail page and the CLI.
- Case risk: each case has impact values C (Confidentiality), B (Integrity) and A (Availability), each 1 to 5, stored as versions by holders of `cases:triage` (migration 0038). The risk score is their mean to one decimal place and shows Not assessed until all three are set. The case list, the case detail and the CLI show it.
- Catalog: versioned entries with versions, corrections, disputes, withdrawals and supersessions (the old version is kept), recommendations (a suggestion with no result), and verification runs that are attached to an entry. Only a passing run verifies it. A restricted reference is returned only with `catalog:read_restricted`. Recommendations have their own list endpoint. The catalog is on the Catalog page of the web UI and in the CLI as `catalog list`, `show`, `add`, `version`, `correct`, `dispute`, `withdraw`, `supersede`, `verify`, and `catalog recommendation list` and `add`.
- Public catalog export: `GET /api/v1/catalog/export` (needs `catalog:read`) and `safe-kit catalog export` return the same versioned JSON (`catalog_export_schema_version` 0.1.0). It carries each entry's public history and no restricted reference, digest or internal identifier. Each export is written to the audit log.
- Export documents (catalog and approved disclosure package): project-defined schemas, not official SAFE schemas. The reading policy is documented in the README: an unknown field is refused, an unknown schema version is refused, and a duplicate ID is refused. Roundtrip tests cover both documents.
- Redaction and TLP: a text/plain evidence item can be redacted into a new item with its own ID, a manifest of the removed line ranges and reasons, and a TLP label that is not less restrictive than the original's. Claims that cite the original are assessed as insufficient evidence on the copy. Evidence reads show the TLP label, and a TLP-hidden item answers the same not-found as a missing one. The CLI has `evidence show`, `derivatives`, `redact` and `show-redaction`, and the case evidence list has a details view with the copies, the manifest and the claims.
- Retention period: `SAFE_RETENTION_YEARS` (a whole number from 1 to 30, required by the API and the worker, set to 5 in `compose.yaml`) is shown for every table in the privacy inventory. The period is provisional and waiting for legal review (decision D-09). Nothing is deleted when it ends.
- One error body for every error: the existing `detail` field plus `error` with a stable `code`, a safe `message`, the `request_id`, `retryable`, and, for validation, `fields` (path and problem, never the rejected value). Request bodies over 256 KiB get `413` `payload_too_large`, except the import and evidence upload routes, which keep their own limits. Validation errors (types, ranges, unknown fields) return `400` instead of `422`; domain refusals stay `422`. Every response carries `X-Request-ID`, taken from the client when well formed, otherwise generated. The readiness endpoint answers `503` in the same error shape.
- The case list pages by cursor: `GET /api/v1/cases` takes `limit` (1 to 200, default 50) and an opaque `cursor`, and returns `items` and `next_cursor` (null on the last page). The `total` and `offset` fields are gone. A bad cursor answers `400` `invalid_cursor`. The CLI `case list` takes `--cursor` instead of `--offset`, and the web case list has Previous and Next buttons.
- Changing a case title: `PATCH /api/v1/cases/{case_id}` takes `title` and needs `cases:triage` and an `Idempotency-Key`. It also needs `If-Match` with the case's ETag, the quoted `revision` from `GET /api/v1/cases/{case_id}` (which also sends the ETag header). A change without it is refused with `428` `precondition_required`; a malformed value with `400` `invalid_if_match`; a stale one with `412` `precondition_failed`, which also sends the current ETag. The revision rises by one only when the title changes. The audit row records the new revision, not the title text. Closed cases refuse the change with `409`.
- Review layer changes need `If-Match` with the review round revision, which is the ETag from `GET /api/v1/reviews/{review_id}`. A change without it is refused with `428` `precondition_required`; a malformed value with `400` `invalid_if_match`; a stale one with `412` `precondition_failed`, which also sends the current revision and ETag. A successful change returns the new ETag. The `expected_revision` body field is removed.
- Review rounds also record conflicts and recusals (`/api/v1/reviews/{review_id}/conflicts` and `/recusals`).
- Deadlines: the 14-day broader advisory is not applicable by default, with a reason, because the case data has no field that records its condition. The weekly update task is due while a significant risk is open, meaning an impact area is recorded as high or critical. Its due date is set when the risk is recorded, and producing an update does not move it. This is the current behaviour; see Not yet implemented.
- Weekly updates: each case with an open significant risk has machine-readable weekly updates, listed and read at `/api/v1/cases/{case_id}/weekly-updates` and `/api/v1/cases/{case_id}/weekly-updates/{update_id}`, and in the CLI as `case weekly list` and `case weekly show`. The document follows `schemas/weekly-update.v0.json`, a project-defined schema that is not an official SAFE schema (schema version 0.1.0). An update is internal: it needs no approval and goes to no external recipient.
- Disclosure packages hold versioned content for one recipient and purpose. A version is previewed, then approved by a person with `disclosures:approve` (`POST .../approvals`). Only an approved version can be exported (`GET .../export`, also `case disclosure export` in the CLI) or recorded in an external notice. Approvals and exports are audited.
- External notices record a notice sent outside the application for an approved version: its send, its receipt (received, or unknown with a reason code), a follow-up, and a cancellation. Each change is a new revision, and the application sends nothing itself. The person who prepared a version may not record a notice of it (`403` `preparer_cannot_record`). A second notice to the same recipient for the same version needs a reason. A closed case refuses these writes. The disclosure screen lists notices and records the send, the receipt, the follow-up and the cancellation.
- Notices are bound to the approved recipient (migration 0049). The approver confirms a recipient reference, an identifier kept outside SAFE, when approving a version (`POST .../approvals`, `case disclosure approve --recipient-ref`). A notice must name the same reference, and any other is refused with `422` `recipient_mismatch`. A version approved before this rule has no reference, so it cannot receive a notice; its package needs a new version and a new approval. The approved recipient name is free text and is not compared.
- An unknown receipt needs a follow-up reason. `receipt_unknown` (`case notice receipt --unknown ... --follow-up-reason`) is accepted only with a follow-up reason. The follow-up is recorded in the same transaction, as the next revision of the notice (`follow_up_required`). Without a reason the request is refused with `422` `unknown_needs_follow_up`. A notice that is unknown and has no follow-up, recorded before this rule, blocks case closure until a follow-up is recorded.
- Model records are versioned and insert-only. A record for a case, an evidence item or a review round names the model, runtime and provider identifiers and the reasoning configuration (mode, effort and budget, never reasoning text). Revocation adds a new version with its reason. Endpoints: `/api/v1/cases/{case_id}/model-records`.
- The overview dashboard (`GET /api/v1/overview/summary`, `GET /api/v1/metrics/timeseries`) shows panels scoped to the caller's role, such as own cases, approvals and weekly updates.
- The API and the worker check their settings against the mode (demo or production) before they connect to the database, and refuse to start on a mismatch. Error messages name the setting, never its value.

### Not yet implemented
- Cursor paging for the other list endpoints (case history, evidence, users and so on); they still use offset paging. The duplicate-key and nesting-depth limits, and the array item limits from the API draft (sections 3.2 and 3.3), are also still open.
- `If-Match` on the other changes: close, reopen, assignments, classification, deadline restore and evidence availability do not check a revision, and no other endpoint checks one. The case revision is raised only by a title change; the deadline task, legal duty and user revisions are separate (see the Added section).
- Deletion at the end of the retention period. The period is shown only, until legal review is complete.
- A production certificate, OIDC/SSO, encryption at rest for the database volume, and backup and restore procedures.
- Disclosure workflow items: recipient review records, package review records, the escalation record, the backup-approver designation, and alerts for a receipt delay or a watched contact. The approved recipient is free text, and a notice is checked against the confirmed recipient reference only, so the recipient name is not compared.
- Anonymous reporter intake. The current reporter channel requires a reporter account. The Vault Transit key provider and object storage for evidence are also not built.
- Verification on Ubuntu 24.04 and 26.04 LTS, which is planned after all other work.
- A case title change command in the CLI. The CLI does not call `PATCH /api/v1/cases/{case_id}`.
- A web UI for the catalog export. The export is available through the API and `safe-kit catalog export`.
- `If-Match` on close, reopen, assignments, classification, deadline restore and evidence availability (see the list above).

### Owner decisions still open

- Whether a weekly update moves its task's due date. Today it does not, so the task can go overdue while updates are produced on time.
- The holiday calendar for deadlines. Today the calendar counts weekends only.

### Not yet verified

- The live three-step demo check (`scripts/demo.sh start`, a browser sign-in as a demo role, and `scripts/demo.sh cli-show`) has not yet been run end to end on a live stack.
